# CLAUDE.md — haybarn-jdbc

Guidance for Claude Code working in this repository.

## What this repo is

**haybarn-jdbc** is the JDBC driver for
[Haybarn](https://github.com/Query-farm-haybarn/haybarn) — an independent
derived distribution of DuckDB ("Haybarn, powered by DuckDB"), published by
Query Farm LLC. This repo is a **hard fork** of `duckdb/duckdb-java` at tag
`v1.5.3.0`.

All Haybarn-specific changes are a small, curated **commit stack** on top of
the upstream tag — not scattered edits. Keep it that way: the stack must
stay easy to rebase onto future upstream tags.

## Hard rules

- **The vendored `src/duckdb/` tree is generated by `vendor.py`.** Don't
  hand-edit it — refresh it by running
  `python3 vendor.py --duckdb /path/to/haybarn-checkout` against a checkout
  of `Query-farm-haybarn/haybarn @ haybarn`. The Haybarn-specific source
  edits (extension trust root, repository URLs, user-agent) live in the core
  fork and flow into this driver through that step.
- **Don't rename the C API header (`duckdb.h`) inside `src/duckdb/`.** That's
  the upstream C surface and Haybarn is intentionally ABI-compatible with
  it. The JNI link uses it as-is.
- **Trademark compliance is mandatory.** Product name is always "Haybarn",
  never "DuckDB Haybarn". DuckDB only appears descriptively
  ("powered by DuckDB", "derived distribution of DuckDB"). Keep the MIT
  `LICENSE` verbatim; keep `NOTICE` accurate.
- **Keep the `DuckDB*` Java class names** (DuckDBConnection, DuckDBAppender,
  DuckDBResultSet, …) so user code that casts to them needs only an
  import-source change. Only `DuckDBDriver` is renamed to `HaybarnDriver`
  (the SPI entry-point class).
- **Keep the internal Java native method names** (`DuckDBNative.duckdb_jdbc_*`)
  and their matching JNI C functions. Renaming would touch the entire JNI
  surface with no migration benefit since these methods are package-private.
- **One commit = one concern.** Prefer additive files over edits to upstream
  files. When you must edit upstream, keep it surgical.

## Building

```sh
make release       # -> build/release/haybarn_jdbc{,_nolib,_tests}.jar
make test          # runs farm.query.haybarn.TestDuckDBJDBC against the build
```

## Releasing

Tag `haybarn-v<version>` triggers `.github/workflows/haybarn-jdbc.yml`:

1. Per-platform JNI build matrix (Linux x64/arm64, macOS universal, Windows
   x64/arm64).
2. Each platform contributes a `haybarn_jdbc.jar` with its native library
   bundled in.
3. `jdbc_maven_deploy.py` combines per-arch JARs into the fat `haybarn_jdbc.jar`
   + per-classifier JARs + sources + javadoc + POM.
4. GPG-signs with the Haybarn release key and uploads to Sonatype Central.

Sonatype OSSRH credentials and the GPG key must be configured as GitHub
secrets — see the workflow file for the required secret names.
